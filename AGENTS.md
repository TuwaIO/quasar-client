# 🤖 Agent Context: Quasar Client (`@tuwaio/quasar-sdk`, `@tuwaio/nova-payments`, `@tuwaio/payments-sdk`)

## 1. Project Philosophy & Goal

- **What is this?** The client side of Quasar: `@tuwaio/quasar-sdk` (the API client for servers, webhook verification, the headless checkout stores, the `quasar-sdk` CLI), `@tuwaio/nova-payments` (the checkout and refunds for React, built on Nova UI Kit) and `@tuwaio/payments-sdk` (both of them as a module on top of `@tuwaio/sdk`).
- **Role in TUWA:** dependencies go one way: Orbit, Pulsar, Satellite and SIWX, then `nova-uikit`, then `sdk`, then this repository, then Quasar. Nothing below this repository may depend on it. A change to the checkout is one commit and one release here, with no round through other repositories. The client parts of x402 and MCP will live here too; what runs on a server stays in the Quasar engine.
- **Philosophy:** no secret key in the browser; the checkout keeps no payment state of its own (the store of `@tuwaio/quasar-sdk/checkout` reads the invoice and follows it); side effects (`localStorage`, network calls, wallet prompts) are explicit and documented.

## 2. Tech Stack

- **Core:** TypeScript 6.0.3 (pinned exactly), Node.js 20+, pnpm 12 (workspace), `tsup` (ESM, CJS, types), `vitest` 5.
- **`quasar-sdk`:** `ofetch`; optional peers `@tuwaio/pulsar-core` (`/pulsar`, and the types of the root entry), `@tuwaio/siwx-react` and `zustand`.
- **`nova-payments`:** React 19.2+, Nova UI Kit 0.15+ (its paper and ink look and the pixel icons of `@tuwaio/nova-icons`, a dependency), Satellite Connect, Pulsar, Orbit, `framer-motion`, optional wagmi + viem and `@solana/kit`.
- **`payments-sdk`:** bundles the two above; peers `@tuwaio/sdk` (0.9+, the first with Nova 0.15), `react`, optional `@tuwaio/solana-sdk`, wagmi, viem, `@solana/kit`, `@solana-program/*`.
- **Docs:** `apps/docs`, Storybook 10 on the model of the Nova UI Kit Storybook, TypeDoc 0.28 + `typedoc-plugin-markdown` 4, `payments.docs.tuwa.io`.
- **Release:** `release-please` (stable, from `main`) and `semantic-release` (`alpha.release.config.js`, prereleases from `feat/**`, `fix/**`, `dev/**`).

```
│   └── payments-sdk/       # Entry points ., ./i18n, ./evm, ./solana, ./checkout, ./styles.css
```

- **How `payments-sdk` is built:** `src/*.ts` are `export *` from the other two; `tsup` bundles them, then `scripts/through-the-sdk.mjs` points every import of Nova, Satellite, Pulsar and Orbit at the entries of `@tuwaio/sdk` (`@tuwaio/solana-sdk` for `@tuwaio/orbit-solana`). An app so has one copy of each, and their React contexts work across the SDK and the checkout. The script fails on a TUWA import without an entry in `ENTRIES`, and a test reads `dist`: when `nova-payments` starts importing a new entry, add it there (and to the SDK if it has no such entry). Keep the `framer-motion` pin equal to the one of `@tuwaio/sdk`. `release-please-config.json` has the `node-workspace` plugin and the module lists the other two as `workspace:` dev dependencies: a release of either also releases the module, which contains its code.
- **`@tuwaio/quasar-sdk/checkout`** (browser): `createCheckoutStore({ token })` is a vanilla Zustand store of one invoice's payment through the checkout routes (`/v1/payments/checkout/:token`, no key): phases `loading`, `buyer`, `selectMethod`, `quoting`, `awaitingPayment`, `submitting`, `confirming`, `unconfirmed`, then the outcome (`paid`, `underpaid`, `held`, `refunded`, `expired`, `cancelled`, `blocked`) or `error`; actions `load` (starts following the invoice: `EventSource` on `events`, a `GET` every `pollMs` without one or after it closed for good), `selectMethod`, `setPayer`, `setConsentGiven` (the merchant's `consent`: a required one not ticked stops `requestQuote` with `consent_required` before any request; a ticked one goes with the quote as `consentGiven: true`; none is asked for the rest of an underpaid invoice, which `requestQuote` prices at the rate of the first quote: `quote.amountDue`, `quote.rateHeldUntil` for an asset that moves against the invoice currency, `checkout.invoice.restPayable` and `originWallet`; the store stays on that payment step while the invoice stays underpaid), `releaseQuote` (back to the methods from a locked quote, also a payerless Solana Pay one), `requestQuote`, `confirmPayer`, `setBuyer`, `setLocale`, `submit`, `relay`, `grantPermission`, `permissionRevoked`, `payAgain`, `destroy`; `receiptUrl`, `paymasterUrl`, `logoUrl`. The view carries what the buyer's page shows (merchant seller details, policy links, `fundingUrl`, `theme`, `consent`, `featured` methods, `review`, `replacedBy`, the subscription period). `api` replaces the HTTP calls (`CheckoutApi`) for tests and simulations such as the docs Playground; pass `EventSource: null` with it. Back to `open` after `processing` means the transaction failed (`payment_failed`, or `unconfirmed` when the engine's reason is not final). `paymentOnTheWay` (read-only state) is `true` from a successful `submit`/`relay` (also a relay answered `sending`, which has no `txKey`) until the payment settles or ends; the engine's `rejectedPayments` (status events and `checkout.invoice`, with `pendingPayments`, `rejectedTxKeys` and `paymentCountsUntil`; `{ txKey, reason, final, userOpHash?, original?, movedMoney?, rechecked?, held?, otherInvoice? }`; `held` on `tx_already_used` = another invoice of the merchant holds the transfer as a held transfer, the error carries `held: true` and says "tied to another invoice", never "pays"; `unresolvedPayments`, `onTimeTxKeys`) listing a key of it (the `txKey`, the hash a sped-up transaction replaced, the relay's `userOpHash`), or no payment on its way plus a rejection not listed at the hand-over, ends it, also on an `open` invoice: the engine's `movedMoney` (or its reasons: wrong amount or recipient, `reference_missing`, `too_early`, `tx_already_used`, `payer_mismatch`…) gives `payment_mismatch` whatever `final` says (it may have moved money: never "nothing was charged", never the re-check promise, F9/N1), back to the payment when final, phase `unconfirmed` when not (no plain second payment); another `final` reason gives `payment_failed` (reverted, cancelled, Solana blockhash expired) and back to the payment (`selectMethod` when the quote expired, L5); any other (`not_found`, `timeout`, `user_operation_lost`…) gives phase `unconfirmed` with `payment_unconfirmed` ("check your wallet before paying again", no pay action; `payAgain()` returns to the payment), with `error.rechecked: true` only while Quasar still reads the payment again (the rejection's `rechecked`, or no rejection and `unresolvedPayments > 0`): only then may the page promise the 24-hour re-check, otherwise it says to contact the merchant with the transaction hash; a Quasar without `rejectedPayments` makes every rejection final. `invoicePaymentOnTheWay` (read-only) mirrors `pendingPayments > 0`: on a payable invoice it puts a reopened page, or one that offered to pay, in `confirming` and the store follows that payment as its own (a payment found on its way that stops counting without a rejection gives `unconfirmed`); `paymentCountsUntil` (read-only) is the engine's on-time flag, never the page clock; `paymentSentInTime` (read-only, F7) matches this page's keys against the engine's `onTimeTxKeys` (`true` once listed and sticky, `false` while listed without them, `null` unknown). `invoicePaymentUnresolved` (read-only, F3) mirrors `unresolvedPayments > 0` (no time limit; `pendingPayments > 0` with an older engine): `load()` with no payment on its way but a newest non-final rejection or an unresolved payment starts in `unconfirmed` (`expired` keeps `expired`) with `payment_unconfirmed`, and a newest moved-money rejection sets `payment_mismatch` (`unconfirmed` too when not final); a newest `not_found`/`timeout`/`replaced` rejection without `rechecked` no longer counts once Quasar reports `unresolvedPayments: 0` (resolved); an expired invoice the store stops following while it is `true` gets `payment_unconfirmed`. `submit` that gets no answer (network, 408, 429, 5xx, `too_many_pending`) keeps `txKey`, gives `unconfirmed` with `payment_unconfirmed`/`submit_retrying`, returns `false` and hands the same `txKey` over again after 2, 4, 8, 16, then every 30 s for up to an hour, per `txKey` (a later payment never stops it), until taken (then followed as usual; taken for an invoice already `paid`/`held`/`cancelled`/`refunded`, the phase stays and the checkout is read once more), refused (other 4xx: `error` set, back to the payment where the page waited for it) or `destroy` (F8); after the hour `error.reason` is `submit_failed` (contact the merchant, N7a). Until taken or refused, the hand-over is kept in `sessionStorage` under `quasar-sdk:checkoutHandOvers:<token>` (`[{ txKey, from?, connectorType?, at }]`; option `handOverStorage`, default `sessionStorage`, none with a custom `api`, `null` keeps nothing), and `load()` hands over again the kept ones Quasar does not list (`rejectedTxKeys`, `onTimeTxKeys`). `409 tx_already_used` from `submit` (Quasar tracks the transaction for another invoice whose page handed it over first, M3) is not a refusal: Quasar records this invoice's claim and credits the transaction to the invoice the wallet that sent it confirmed, so the store follows it as its payment with phase `unconfirmed` and `payment_unconfirmed`/`tx_already_used` (cleared when the invoice becomes `processing` or settles; a `tx_already_used` rejection of it gives `payment_mismatch`), never hands it over again and never keeps it in the tab. A `settlement_failed` rejection (confirmed on chain; `movedMoney`, not final) is `payment_unconfirmed`/`settlement_failed`, not `payment_mismatch`; its text promises the daily retry, with `error.rechecked`, only while the engine marks it `rechecked` (30 days). `payAgain()` does nothing for either: the payment left the wallet. Never let the page offer to pay while a payment may still arrive. `expired` or `cancelled` while `paymentOnTheWay` (or `invoicePaymentOnTheWay`) does not stop it (`cancelled` is no longer a settled state; a hand-over taken on a cancelled invoice is followed with the phase kept, and a reopened cancelled invoice with an unresolved payment gets `payment_unconfirmed`): it keeps the stream while the engine keeps it open (`pendingPayments > 0`), otherwise closes it (a browser `EventSource` would reconnect every few seconds) and reads every 20 s, until `paid` (the engine's 30-minute grace for a payment it learned of before `dueAt`), `held` (a late payment), a failure, a read with `pendingPayments: 0`, `followingUntil` (read-only, ISO; `null` while not limited: 35 minutes past the later of `dueAt` and the latest hand-over, a payment found on its way counting from when the store found it; an hour after the expiry without `dueAt`; 35 minutes after the later of when the store found the invoice cancelled and the latest hand-over; a later hand-over moves it on), or `destroy`; the store never expires an invoice by the clock, and past `followingUntil` the page learns nothing without a reload (say until when it follows, never that it shows the outcome whenever it comes). Payer proof (engine 2026-10-29, owner: one free signature before an EVM payment the buyer's wallet sends, after wallet and method, before the price; one per invoice and wallet): `payerProof` (read-only) is `not_needed` (no method, Solana `none`, an engine without `methods[].payerProof`), `required` (`before_quote`, or after a `409 payer_proof_required` of the quote; `requestQuote` refuses locally with `payer_proof_required`), `unless_relayed` (the relay's EIP-3009 authorization confirms; a transfer or paymaster payment needs `confirmPayer` first; it stays `unless_relayed` while a prompt is open, so a cancelled one never blocks a new price), `confirming` (only a `before_quote` wallet's prompt), `confirmed`; a failed or declined later attempt of a wallet confirmed meanwhile sets no error; `requestQuote` on an underpaid invoice may get `409 payer_mismatch` with `error.originWallet` (pay the rest from the wallet that paid first); `createRefundStore` puts `details.invoice` of `409 payment_held_elsewhere` in `error.otherInvoice` (from `checkout.payerProofs`, this page's confirmations, or `quote.payerProof.proven`; `eoa`/`authorization` count on every EVM network, a smart wallet's and a `proven` message answer only on their network; EVM addresses compared case-insensitively). `confirmPayer(sign)` posts `payer-proof/message { payer }`, skips signing when it answers `proven`, calls `sign(message, request)` (the page's `personal_sign`; a rejection is `payer_proof_declined` and sends nothing), posts `payer-proof { payer, message, signature }`; refusals keep their `code` and `details.reason` as `error.reason` (`payer_proof_invalid` `message_mismatch`/`signature_invalid`, `payer_proof_unavailable` `rpc_failed`, `payer_not_expected` → `blocked`); `payer_required` without a wallet. `CheckoutApi.payerProofMessage`/`payerProof` are optional for older simulations (then `request_failed`). A transfer tied to no invoice never holds the invoice: `payer_mismatch` and `payer_unconfirmed` rejections are final and moved money, and with `held` (a held transfer of its own) the `payment_mismatch` error says the merchant returns it to the wallet that sent it and the invoice can still be paid; without `held` it promises no refund. Webhooks: `data.hold` (`PaymentWebhookHold`) of `invoice.held`; `invoice.transfer_held` and `invoice.transfer_hold_voided` with `data.heldTransfer` (`PaymentWebhookHeldTransfer`, `PaymentWebhookHeldTransferVoided`). The payments module lists held transfers (`listHeldTransfers`) and refunds one (`refundHeldTransfer`); `Refund.heldTransfer` names it. One store serves a subscription's first payment (the view's `autoCharge`). `createRefundStore({ request, submit, get })` refunds from the merchant's wallet through calls the app runs on its server; a transaction the wallet sent stays in `sentTransaction` and in `sessionStorage` under `quasar-sdk:refundHandOvers` (option `handOverStorage`) until Quasar takes it or refuses it for good (4xx other than 401, 403, 408, 425, 429), and `start` for the invoice brings its refund back instead of asking for a second one. Neither sends a transaction.
- **`@tuwaio/quasar-sdk`**: `Quasar` (`pulsar: PulsarModule`, `payments: PaymentsModule`), `QuasarSDKError` (HTTP `status`, `originalError`, and from the Payments API `code`, `issues`, `details`), `BASE_API_URL`, `PULSAR_SYNC_ENDPOINT`, `PULSAR_HISTORY_ENDPOINT`, `pulsarSyncHashEndpoint`, `PAYMENTS_ENDPOINT`, `QuasarConfig`, `HistoryQuery`, `PaginatedResult`, the re-exported Pulsar `Transaction` types (values only in `/pulsar`, with `watchBatchHashes`: EIP-5792 batch hashes from a Pulsar store, for `syncHash`), the Payments types (hand-written from the engine's views: Quasar's shared package is private) and `verifyWebhook` (Web Crypto HMAC-SHA256 of the raw body in constant time; a delivery outside `toleranceSeconds` of its `sentAt` is `stale`, a transaction webhook without `sentAt` (engines before Payments) is checked by its `timestamp`, neither is `stale`; `toleranceSeconds` other than a finite number above 0 or `false` is `invalid_options`). `PaymentsModule` encodes IDs as path segments, sends dates as ISO 8601 and `idempotencyKey` as the `Idempotency-Key` header, and downloads documents with `QuasarClient.requestFile`. Requests send the secret key in `x-tuwa-secret-key` (and `x-internal-secret` when set; only the Quasar dashboard uses it). `/react`: `preFlightTxCheck` (SIWX session in `useSiwxSessionStore` + `GET /v1/engine/monitoring/health`). CLI: `quasar-sdk listen` streams the deliveries of webhook endpoints with a `localhost` URL from `/v1/engine/webhooks/listen` (signing secret in the `x-webhook-secret` header) and posts them to `--forward-to`.

## 4. Coding Standards (STRICT)

- **Language:** English only in code, comments, commits and docs, except the translations in `apps/docs/i18n` and the languages of the checkout (`packages/nova-payments/src/i18n`). The checkout ships no Russian.
- **Types:** strict TypeScript, no `any`.
- **Comments:** JSDoc for all exported functions, types and constants in `packages/*/src`, with inputs, outputs, errors and side effects. It is published as the reference page of the export. `{@link X}` only for symbols of the same package.
- **READMEs** (`packages/*/README.md`) are both the npm page and the docs page: absolute URLs only; no hand-written lists of exports; document browser storage and contacted hosts; every example must compile.
- **Comments never cite plans**, reviews or dates of decisions: they say what the code does and why.

## 5. Key Workflows

```bash
pnpm build        # builds the packages
pnpm test         # vitest in every package
pnpm lint         # ESLint
pnpm typecheck    # tsc over packages, apps and scripts
pnpm format       # Prettier

pnpm storybook    # the docs site on port 6006
```

Stories run in Chromium with axe only in the `Tests` workflow (`pnpm --filter @tuwaio/quasar-client-docs test:stories` locally after installing Playwright's browser): read it as well as `Alpha Release` after a push.

## 6. AI Agent Behavior (Mandatory)

- After changing code: `pnpm lint --fix` and `pnpm format`. After changing exports, JSDoc or a README: `pnpm docs:gen`, with no warnings.
- After changing the API types or endpoints of the Quasar API: `pnpm openapi:gen`.
- After changing `apps/docs/src/Introduction.mdx`, update both translations in the same change: a translation keeps the code blocks and links of its English page, and never use «рушій».
- Never install new packages without explicit permission.
- Never push to `main`: it goes through the owner, by a pull request he merges.
- Do **NOT** import `@tuwaio/sdk` in `quasar-sdk` or `nova-payments`: only `payments-sdk` knows it.
- The checkout is drawn in the paper and ink of Nova 0.15 (`paperAndInk.test.tsx` guards it). Do **NOT** import `@heroicons/react` in `nova-payments`: its icons are in `src/components/icons.tsx` and follow the icon set of `NovaIconsProvider` (the names of the Nova set through `NovaSetIcon` of `@tuwaio/nova-core`; the icons only the checkout draws from the set when it has them, as the Heroicons set of `@tuwaio/nova-core` 0.15.1 does, else the pixel ones of `@tuwaio/nova-icons`, which keeps the checkout working with `@tuwaio/nova-core` 0.15.0). Do **NOT** write `rounded-full`, a shadow, a gradient or `animate-spin`: a mark that was a circle is `rounded-[var(--tuwa-rounded-full)]`, a surface has a line of 1 px, the wait for a wallet is `novapay-chase`. Buttons, labels and chips take their letters from `caps`, `label`, `chip`, `primaryAction`, `secondaryAction` and `smallAction` of `src/components/classes.ts`; a button label with a name in it (a seller, a wallet, a network) is filled with `capsLabel`, so the name keeps its own letters. A block that fills itself with the color of its surface carries `tuwa-scanlines`.
- Do **NOT** add a Quasar Cloud or TUWA secret to anything that runs in the browser.
- Do **NOT** import React, SIWX, `zustand` or a value of `@tuwaio/pulsar-core` in the root entry point of `@tuwaio/quasar-sdk`: a webhook handler loads it on every cold start. Browser code goes to `/react`, `/checkout` and `/pulsar`. Do **NOT** use the secret-key client (`QuasarClient`) in `/checkout`: the checkout opens one invoice with its token, and the refund store calls functions the app runs on its server.
- Do **NOT** put secrets in URLs (the CLI sends the signing secret in the `x-webhook-secret` header), and do **NOT** document creating `Quasar` in the browser.
- Every response schema in `scripts/` is assigned to the type the SDK returns for it (`const _checkX: z.ZodType<X> = XSchema`), so `pnpm typecheck`, part of the `Tests` workflow, fails when the description and the SDK types drift apart.
